# 이력서 검색 실험: 키워드 / Static-64 / E5 Tiny

## 결론

**다음 검증 후보는 E5 Tiny입니다. Static-64를 지금 검색의 대체재로 채택할 근거는 부족합니다.** 두 모델 모두 이력서 본문에 연결하거나 배포하지 않았습니다. 운영 사이트 파일은 변경하지 않았습니다.

이 실험은 공개 main `4a1e9798d7414df244348b1af313300293702157`의 **실제 프로젝트 5개**와, 그 내용을 바탕으로 미리 작성한 **진단용 합성 질의 30개**를 사용합니다. 전체 이력서 검색이 아니라 프로젝트 카드 5개 안에서의 순위 비교입니다. 실제 채용공고 표본, 독립적인 품질평가, 모바일 성능평가는 아닙니다. 질의와 정답을 같은 프로젝트 내용에서 만들었으며 별도 홀드아웃이 없습니다. 작성 시점의 사전 고정을 증명하는 기록도 없으므로 개발용 진단 집합으로 취급합니다. 작은 표본이므로 결과를 일반적인 정확도로 해석하면 안 됩니다.

## 측정 결과

표는 의도한 프로젝트가 첫 번째 관련 결과로 나온 횟수입니다. 키워드 검색은 점수 0인 기본 나열을 검색 성공으로 세지 않습니다. 원래 UI는 이 경우에도 카드를 숨기지 않습니다.

| 질의 종류 | 개수 | 기존 키워드 | Static-64 | E5 Tiny |
|---|---:|---:|---:|---:|
| 기술명·명시적 표현 | 10 | 9 | 10 | 10 |
| 한국어·영어 바꿔 말하기 | 10 | 1 | 2 | 10 |
| 공고 형태의 짧은 문단 | 2 | 2 | 2 | 2 |
| 요건이 뒤에 있는 긴 문서 | 2 | 2 | 0 | 1 |

나머지 6개는 무관한 직무, 미기재 기술, 부정문, 빈 입력, 무작위 문자열을 점검합니다. 성공률에 섞지 않았습니다. 케이스별 점수와 순위는 `results-node.json`, 계산 결과는 `summary.json`에 있습니다.

### 실제로 좋아진 예

- “카메라로 사람의 움직임을 알아내어 활동량을 재는 시스템”: 키워드 검색은 인식 항목이 없고 Static-64는 다른 프로젝트를 먼저 선택했습니다. E5는 아동 운동량 측정 프로젝트를 먼저 선택했습니다.
- “Display electricity generation trends in an interactive web interface”: E5는 태양광 대시보드를 먼저 선택했습니다. 다른 두 방식은 원하는 프로젝트를 첫 관련 결과로 찾지 못했습니다.

### 여전히 막아야 할 문제

- **긴 문서:** E5는 2,375 / 2,011 토큰 입력을 512개로 잘라 뒤쪽 요건을 읽지 못했습니다. 한국어 예에서 첫 결과가 맞은 것은 요건을 읽었다는 증거가 아닙니다. Static-64는 자르지 않지만 회사 소개의 반복에 희석됩니다. 두 입력에서 사람이 요건 부분만 따로 떼어 넣으면 두 모델 모두 맞았습니다. 이는 분할의 필요성을 보여주는 대조 실험이며, 자동 요건 추출기를 구현했다는 뜻이 아닙니다.
- **미기재 기술:** “Kubernetes Rust React 필수”에도 E5는 어떤 프로젝트를 약 0.410의 유사도로 먼저 골랐습니다. 이는 실제 관련 질의의 0.321보다 높습니다. 이 표본만으로 단일 유사도 임계값을 정하거나 기술 충족률을 표시하면 안 됩니다.
- **부정문:** “Vue.js나 D3.js 경험은 필요 없습니다. Python 이미지 인식 서버 경험을 찾습니다.”에서 기존 키워드 방식은 Vue/D3가 있는 대시보드를 먼저 올립니다. E5는 원하는 결과를 먼저 골랐지만, 대시보드와의 차이는 약 0.004에 불과합니다. 부정을 안정적으로 이해한다고 볼 수 없습니다.
- **빈 입력 / 무관한 입력:** 임베딩은 가장 가까운 벡터를 반환할 뿐, 적합한 경험이 있다는 보장은 하지 않습니다. 빈 입력은 추론 전에 차단하고, 관련 결과 없음 처리를 별도로 설계해야 합니다.

## 실행 가능성과 비용

두 모델 파일을 고정 리비전으로 내려받고 SHA-256을 기록했습니다. 원격 Python 코드나 모델 저장소의 스크립트는 실행하지 않았습니다.

| 항목 | 검증된 바이트 |
|---|---:|
| Static-64 가중치 + 토크나이저 | 8,944,095 |
| E5 qint8 ONNX + 토크나이저 | 41,207,536 |
| 현재 하네스의 Transformers.js 브라우저 파일 | 1,777,240 |
| ONNX Web WASM 바이너리 | 11,210,254 |

모델 크기는 전체 브라우저 전송량이 아닙니다. E5에는 위 런타임과 작은 JS/config 파일도 필요합니다. 브라우저 캐시, 압축, 번들 최적화에 따라 실제 전송량이 달라집니다. `runtime-sizes.json`의 gzip 수치는 파일을 로컬에서 압축한 크기이며 실제 배포 전송량 측정이 아닙니다. Static-64 자체는 단어 벡터 조회·평균만 필요하므로 WASM 추론 런타임이 필요 없습니다.

**E5의 ARM64라는 파일명은 이번 환경의 이식성을 막지 않았습니다.** ONNX Runtime Web 1.22.0의 단일 스레드 WASM 백엔드에서 x86 Node.js로 384차원 출력을 생성했습니다. ARM64 네이티브 실행을 한 것은 아닙니다.

짧은 긍정 질의 22개를 각각 3회 실행하고 후반 2회씩 44개 시간을 계산했습니다. 한 프로세스/세션에서 같은 질의를 연속 실행한 상관된 측정이며, 44개의 독립 표본이나 통계적 성능 보장이 아닙니다. 아래 값은 리팩터링 후 재실행한 값으로, 초기화에는 모델 해시 검증도 포함됩니다.

| Node WASM/JS 측정 | Static-64 | E5 Tiny |
|---|---:|---:|
| 질의 중앙값 | 0.041 ms | 21.87 ms |
| 질의 p95 | 0.140 ms | 61.45 ms |
| 로컬 파일 로딩·초기화 | 56.9 ms | 680.8 ms |
| 프로젝트 5개 임베딩 생성 | 4.81 ms | 533.67 ms |

**이 수치는 브라우저나 모바일 성능이 아닙니다.** 클라우드 컨테이너의 Node v24에서 실행했으며, 로컬 모델 파일을 사용해 인터넷 다운로드 지연은 제외했습니다. 별도 Chromium 실행은 socket 권한 오류로 실패했고, 관리형 브라우저는 로컬 서버에 접속하지 못했습니다. Safari/iOS/Android, 최초 다운로드, 실제 메모리, UI 멈춤, 브라우저 캐시는 미검증입니다.

## 구현·검증 범위

- 원본 `index.js`의 순위 함수와 정렬 규칙을 테스트용 어댑터에서 그대로 사용합니다. 운영 코드는 수정하지 않습니다.
- Static-64는 special token 없이 합산 후 L2 정규화합니다. 평균 후 정규화와 동등합니다.
- E5는 `query: ` / `passage: ` 접두사, attention mask 평균 풀링, L2 정규화를 사용합니다.
- Transformers.js 일반 토크나이저의 긴 입력 절단에서 마지막 SEP가 사라지는 차이를 발견해 실험 어댑터에서 복원했습니다. 수정 후 **두 모델 각각 질의 30/30, 프로젝트 문서 5/5, 요건 전용 대조 2/2, 경계 입력 8/8의 token ID가 독립 Rust 토크나이저와 일치**합니다. E5 문서는 49–84 토큰으로 잘리지 않습니다. E5 임베딩 수치 자체의 독립 구현 대조는 아직 하지 않았습니다.
- Static-64의 150개 유사도는 별도 Python/NumPy 구현과 최대 절대오차 약 `3.33e-16`로 일치합니다.
- Node 테스트 **23/23**, Python 지표 테스트 **6/6**, JS/Python 구문 검사, 기존 `generate_resume.py --check` 통과. 스냅샷 일치와 실제 로직의 오류/경계 테스트를 함께 수행합니다.
- `provenance.json`에 운영 파일 5개의 원본 해시를 기록하고 테스트에서 확인합니다.
- `core.mjs`와 `encoders.mjs`를 브라우저/Node에서 직접 가져옵니다. 이전 Node 실행기의 소스 문자열 치환과 가짜 DOM 전역을 제거했습니다.
- 모델을 사용하기 직전에 크기/SHA-256을 확인하고 결과를 코드·질의·코퍼스·의존성 잠금 파일의 해시에 연결합니다. 검증기와 요약기, 테스트는 오래된 결과를 거부합니다.
- 실패한 모델이 있으면 결과를 불완전 상태로 저장하고 CLI는 실패로 종료합니다. 세션을 해제하며, 페이지는 실행 중 중복 호출과 저장 실패를 표시합니다.
- 로컬 서버는 요청 크기를 읽는 동안 제한하고, 같은 출처의 JSON 저장만 허용하며, 경로/심볼릭 링크 탈출을 거부합니다. 서버 동작은 요청 핸들러 단위 테스트로 확인했습니다. 실제 브라우저 E2E 검증은 아닙니다.
- `review.md`에 독립 검토의 발견점과 남은 검증 범위를 정리했습니다. 순위 함수/질의/코퍼스는 변경하지 않았고 이전 결과와 90개 순위 목록이 모두 일치합니다.

## 재현

Node 22+, Python 3.9+, npm, 모델 다운로드 인터넷 연결이 필요합니다. 모델 파일은 합계 약 50MB이며 저장소에 포함하지 않습니다.

```sh
cd experiments/search
npm ci
python3 download-models.py
node run-node.mjs
python3 summarize.py
python3 -m pip install tokenizers==0.22.1 numpy
python3 verify-tokenizers.py
npm test
python3 -m unittest test_summary.py
python3 ../../scripts/generate_resume.py --check
```

브라우저를 실행할 수 있는 기기에서는 아래 명령이 표시한 로컬 URL을 열고 “Run benchmark”를 누릅니다. 완료 결과는 같은 디렉터리의 `results.json`에 저장됩니다. 이 경로는 아직 실제 브라우저 검증 전입니다.

```sh
node run.mjs --serve
```

독립 Chromium을 실행할 수 있으면 `CHROMIUM_PATH=/path/to/chromium npm run benchmark`도 가능합니다. 경로를 생략하면 Playwright에 설치된 Chromium을 사용합니다. Chromium 설치는 별도이며 이 패치에 포함되지 않습니다. 모델 경로는 다운로드/Node/브라우저/검증 모두 `MODELS_DIR`로 바꿀 수 있습니다. `python3 download-models.py --verify-only`로 네트워크 없이 기존 모델 파일을 검사할 수 있습니다. `RESULTS_FILE`은 실행기와 분석기에서 다른 결과 파일을 선택하며, 기본 테스트는 체크인한 `results-node.json`을 검증합니다. 로컬 서버는 127.0.0.1에만 바인딩하며 공개 배포 서버로 사용하지 않습니다. 진단용 빈 입력까지 실행하므로 하네스를 운영 검색에 그대로 연결하지 마세요. 브라우저 리소스 표는 측정 시작 전 JS 모듈 로드를 포함하지 않으며, 현재 no-store 서버로 캐시 성능을 결론 내릴 수 없습니다.

## 다음 검증 순서

프로젝트 공통 기준은 [TESTING.md](../../TESTING.md)입니다. 코드화된 계약 검증을 먼저 실행하고, 그 계약으로 판단할 수 없는 연결·성능·UX만 실제 브라우저에 남깁니다.

1. 현재 UI의 공개 근거·입력 비공개·URL/DOM 상태 계약부터 코드화합니다. 기존 실험 테스트 통과를 운영 UI 검증으로 간주하지 않습니다.
2. 실제 공고 기반 독립 라벨과 holdout을 준비하고, 빈 입력·관련 없음·부정문·긴 문서 정책을 development 집합에서 검증합니다. 현재 30개 진단 질의에 임계값을 맞추지 않습니다.
3. 명시 기술은 근거 데이터에서만 표시하고 의미 유사도는 별도 관련 경험으로 다룹니다. 향후 분할/합산을 구현한다면 독립 품질평가와 E5 수치 대조를 추가합니다.
4. 하위 계약이 통과한 뒤 MacMini에서 코드화된 작은 브라우저 smoke를 수행하고, 목표 기기에서 최초 다운로드·cache·메모리·UI 응답을 따로 측정합니다. Mac desktop 결과를 모바일 통과로 보지 않습니다.

이 순서는 검증 기준이며 모델 채택·운영 구현·배포 승인이 아닙니다.
